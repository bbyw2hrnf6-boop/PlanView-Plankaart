# PlanView Plankaart

A static, local-first research prototype for Limburg planning maps. The street basemap stays visible at every zoom; the map button cycles Street, BGT detail and Aerial. The default clean rendering keeps plan fills translucent so roads and building outlines remain legible. On macOS, double-click `PlanView starten.command` on the Desktop. It starts this project’s server in the background and opens the correct localhost URL. You can also run `python3 launch_planview.py` from this folder. The launcher uses port 4174 or the next free port through 4184. When Codex CLI is installed and signed in with ChatGPT, the local server uses that existing Codex sign-in to run `gpt-6-luna` at low reasoning effort; no Platform API key is needed. This consumes your Codex usage. An `OPENAI_API_KEY` is optional as a fallback or when `PLANVIEW_AI_BACKEND=api`. The browser never receives credentials. The static interface also runs on GitHub Pages, but live AI interpretation there requires a separately hosted authenticated API; static Pages cannot directly access a local Codex session or protect an API key. Live maps and search also depend on external PDOK, OpenStreetMap and Esri services.

## Project files

- `index.html` — app shell and controls.
- `styles.css` — responsive design.
- `app.js` — map, PDOK requests and source ranking.
- `smart-search.js` — advanced search, map-area marking, sample matching and local fallback interpretation.
- `server.py` — local static server and GPT-6 Luna interpreter through signed-in Codex CLI (API fallback); no third-party Python packages required.
- `launch_planview.py` — starts/reuses a detached localhost server and opens the browser.
- `search_filters.schema.json` — constrained filter output for Codex and API model calls.
- `layer-help.js` — brief English, Dutch and German definitions for each layer and legend category; hover or click the small info buttons.
- `i18n.js` — English, Dutch and German interface labels; official plan names and legal values remain in Dutch.
- `limburg.json` — province and municipality boundaries.
- `data/bouwvlakken/` — province-wide tiled bouwvlak polygons and a small search index derived from the official PDOK Wro extract.
- `update_bouwvlakken.py` — streams the national PDOK Bouwvlak GML and rebuilds the Limburg tiles. Run when a new extract is published.
- `vendor/`, `legend/` — bundled map libraries and legend images.

## Data method and limits

A click sends PDOK `GetFeatureInfo` requests for the exact point. The returned `enkelbestemming` geometry supplies the main designation and IMRO plan ID. The app matches that ID to the `plangebied` document metadata and ranks the direct geometry-linked plan above unrelated municipality documents. Parcel geometry comes from the cadastral WMS. Other enabled planning overlays are fetched after the primary result. Check current legal effect and supplementary rules in the Omgevingsloket.

The **Advanced search** lives under the top search bar. Choose the visible Limburg map, one municipality, the whole province, or a drawn rectangle. Choosing municipality scope while the sidebar still shows all Limburg uses a municipality named in the question, or the municipality under the map center when zoomed in. A request for the “marked area” starts rectangle drawing if none exists, then resumes the search. The search uses spatial tiles derived from the [official PDOK Bouwvlak download](https://www.pdok.nl/atom-downloadservices/-/article/ruimtelijke-plannen). Small scopes load full local index tiles; large scopes load a 0.01-degree spatial overview to keep the browser responsive. Candidate points are inside actual Limburg bouwvlak polygons. A candidate qualifies only when the zoning feature at that point references the same IMRO plan and designation polygon as the indexed bouwvlak; results show the precise bouwvlak outline, ID, plan status and date. PDOK `GetFeatureInfo` remains a fallback for other sampled points. Sites missing a confirmed envelope at the tested point appear only as separately labeled review leads. The index covers the province, while **search results still screen a bounded sample of candidate points, not every parcel**. This avoids claiming complete site discovery.

The search also reads a compact, locally cached [TOP10NL OGC Features](https://api.pdok.nl/kadaster/brt-top10nl/ogc/v1/collections?f=json) snapshot of campsites, populated places, industrial areas, parks, sports grounds, cemeteries, swimming-pool complexes, and marinas for Limburg, plus [ProRail Spoorwegen](https://www.pdok.nl/ogc-webservices/-/article/spoorwegen) station points. Regenerate it with `python3 update_context.py`; the resulting `data/limburg_context.json` is committed for fast, dependable local use and GitHub Pages compatibility. The user question and a bounded map/context summary go to GPT-6 Luna for validated filter interpretation. If Codex or an API key is unavailable, the UI clearly labels its limited local parser. Candidate points are screened by approximate feature-extent distances. PDOK `GetFeatureInfo` checks zoning polygons, IMRO sources and mapped building footprints at those points. Matching **plan polygons**, exact bouwvlak outlines and numbered points appear on the map with distance evidence. For potential-building-land searches, areas that fit the surroundings but fail a bouwvlak or unbuilt check appear as dashed orange **review leads**, separately from exact screening matches. A request for quietness also produces review leads until a proper noise dataset is connected. TOP10NL, ProRail, and plan data have different update schedules; distances to feature bounding extents are approximate. The supported nearby-object types live in `search_filters.schema.json`, `smart-search.js`, and `update_context.py`; add a source and mapping in all three when extending the vocabulary. An unbuilt bouwvlak does not prove ownership, availability or a building right. Production search should also spatially index parcels, current DSO Omgevingsplan rules and validated noise data, then return paginated parcel/plan records with source IDs and legal-effect checks.

For the local Codex route, check `codex login status`. If it is not signed in, run `codex login` once in Terminal and complete the normal ChatGPT sign-in, then restart PlanView. Each advanced-search submission invokes a short-lived, read-only `codex exec` process with `gpt-6-luna`, `model_reasoning_effort=low`, and a JSON output schema. The model translates words into filters; PDOK supplies the actual plan evidence. The server binds only to `127.0.0.1`, validates the browser origin and request size, and never serves dotfiles or Python source. Search text goes through your Codex account to OpenAI; the UI shows which interpreter is active. If neither Codex nor an API key is available, the limited local phrase parser remains usable. No credentials belong in this repository or in GitHub Pages.

The optional [**NOVEX planned housing locations** WMS](https://www.pdok.nl/-/regionale-woondeals-en-novex-woningbouwlocaties-beschikbaar-op-pdok) draws officially published housing locations across its available coverage. It does not cover all potential sites in Limburg. Advanced search can require a building envelope and no mapped building at sampled points. This is a research clue, not a probability or permission to build. A residential designation does not prove that land is vacant, available, buildable, or permissible for a proposal. Assessment needs current Omgevingsplan rules, parcels, environmental constraints and authority review. PDOK also publishes [planned land use from DSO](https://www.pdok.nl/ogc-webservices/-/article/gepland-landgebruik-dso-lv-omgevingswet-inspire-geharmoniseerd), but its designations likewise do not certify buildability. The Wro spatial plans service used by this prototype is [updated semiannually](https://www.pdok.nl/ogc-webservices/-/article/ruimtelijke-plannen).

## Map-first interface (September 2026)

The production entry point is still `index.html`. `interface.css` provides semantic theme tokens and responsive layout; `interface.js` adds the workspace around the existing `app.js` map/data adapters. No mockup screenshots, synthetic parcel records or generated map imagery are used in the live app.

- **Explore:** starts at detailed Maastricht plankaart scale. Municipality selector and Fit province retain all 31 Limburg municipalities. Planning and Context presets use the existing layer switches. Layer labels report loading, unavailable tiles and zoom-dependent visibility. Official category colours remain consistent across themes.
- **Inspect:** click the map or a search result. Summary, Rules and Sources tabs retain real PDOK geometry, cadastral parcel, plan metadata, original rule links and the “Why this source?” explanation. Secondary instruments remain visible under Sources.
- **Search:** existing local Codex interpretation, Limburg context snapshot and bouwvlak index remain connected. Manual criteria offer an alternative with explicit station, park and industry distances in kilometres. Distances are approximate screening checks. Matches/review tabs filter both the result list and map; hovering a result highlights its geometry. Cancel stops further work and labels any retained results partial.
- **Compare:** add up to three inspected sites or search results. Compare source-linked evidence, then reopen a site to query fresh data. Unknown or unqueried data is labelled explicitly. Export downloads the comparison as JSON.
- **Cases:** existing saved locations are preserved. Saving an inspected site adds an evidence snapshot; notes stay on this browser/device. Site brief export downloads plain text. Export or back up important work: local storage is not a shared case-management database.
- **Map tools:** rectangle search area, two-point straight-line measurement, original street/aerial/BGT modes and MapLibre perspective view. Perspective tilts the source map; it is not an authoritative 3D development model.
- **Street context:** a small real Esri aerial preview accompanies desktop selections. Street View opens an external Google Maps panorama search for the selected coordinates; imagery availability is not guaranteed. There is no generated street photograph presented as evidence.
- **Appearance:** Day, Night, Sand and System persist in `planview-appearance`. English, Dutch and German remain available. Some official plan terms and exported technical evidence intentionally retain their source wording.
- **Mobile:** bottom navigation, an expandable inspector, layers sheet and two-tap area marking. Tap opposite corners to define a rectangle. Scroll inside panels; the map workspace itself does not scroll.

The existing Desktop launcher still targets this project and starts the Python local server. Static hosting continues to serve maps and manual/local-parser search where upstream services permit it. The local Codex AI endpoint requires `server.py` running on localhost; GitHub Pages cannot run that backend.

### UI integration contract

`smart-search.js` exposes a small `window.planviewAdvanced` controller (`setOpen`, `startDrawing`, `cancelDrawing`, `runManual`, `cancel`, `filterResults`). It dispatches `planview-search-open`, `planview-search-busy` and `planview-search-results` events for the interface shell. The shell does not replace the underlying provider APIs, source ranking or cached Limburg datasets. Theme and comparison preferences are separate from the existing `planview-saved-v1` records. New saved evidence fields are additive for backward compatibility.

Search still samples locations; it does **not** enumerate every parcel in Limburg or establish a legal right to build. A mapped bouwvlak is source evidence, not planning permission. Check current Omgevingsplan rules and supplementary instruments in Omgevingsloket.

## Source-backed development and campsite context

The **Development Context** section keeps the existing NOVEX WMS unchanged and includes **Provincial Planning** and **Planned Housing & Construction Projects**. Provincial Planning reads a local GeoJSON snapshot of [Provincie Limburg planning geometries](https://portal.prvlimburg.nl/geodata/PROVINCIALE_BELEIDSPLANNEN/wfs): urban areas, nature network and groundwater protection. It is strategic context, not a parcel-level building right; current legal effect must be checked in the [Omgevingsloket](https://omgevingswet.overheid.nl/regels-op-de-kaart/). At province zoom, only urban polygons render; finer protection geometries appear as the user zooms in. The projects layer reads `data/development_projects.geojson`; its initial verified entry is Maastricht's [KPN-Vikingsite](https://www.gemeentemaastricht.nl/stad/actueel/persbericht/voormalige-kpn-locatie-ontwikkelt-zich-tot-levendige-plek-binnen-het) announcement. Its marker location is approximate, not a project boundary, and other municipalities have no imported project records yet. All overlays filter to the visible area and load only when switched on.

**Camping & Holiday Parks** appears under **Context**. `data/camping_sites.geojson` contains 252 campsite, caravan-park and bungalow-park polygons from [PDOK TOP10NL functional-area features](https://api.pdok.nl/kadaster/brt-top10nl/ogc/v1/collections/functioneel_gebied_vlak/items). `update_camping_sites.py` rebuilds the local snapshot; `update_provincial_context.py` rebuilds provincial context. Both snapshots work on localhost and GitHub Pages without a runtime data key. The campsite boundary is topographic, not a legal designation. Advanced Search distinguishes **inside** (point-in-polygon against the actual site geometry) from **near** (approximate distance to mapped boundary). Search is still sampled and not a full parcel inventory. Queries about tiny houses, chalets or permanent occupation surface the intersecting IMRO plan and a link to its official rules, while explicitly marking permission **unverified**. Current Omgevingsplan rules, use restrictions, building envelopes and occupancy terms require human review; recreation zoning alone is insufficient evidence.

## Building Insights on the local server

Click a registered building footprint to add **Building Insights** to the existing Summary panel. The browser asks the [PDOK BAG OGC API](https://www.pdok.nl/ogc-apis/-/article/basisregistratie-adressen-en-gebouwen-ba-1) for the **pand** polygon containing that exact point, then reads its BAG ID, construction year, status, use and linked **verblijfsobject** (VBO) records. Multi-unit buildings have an address selector. A click outside a registered footprint adds no building card. This BAG-only feature needs no API key, adds no map layer or colour and also works on GitHub Pages when the official BAG service is reachable.

The first **Summary** section also shows the official **Bouwvlak** at every selected plan point. Normal map clicks reuse the PDOK WMS building-envelope query when that layer is on and make a point-only query when it is off. Advanced Search selections carry the matching ID, IMRO plan, date and status from the locally indexed [PDOK Wro Bouwvlak extract](https://www.pdok.nl/atom-downloadservices/-/article/ruimtelijke-plannen) into the same panel. Each matched feature links to its source plan in Omgevingsloket and to the PDOK geometry source. The panel distinguishes a confirmed footprint, an indexed feature missing from the current point response, no footprint returned and an unavailable source. A mapped Bouwvlak is evidence of published plan geometry, not proof of a current building right.
